# Notes: where the brief was unclear, wrong or missing something

- What I was given is a binary NES ROM. The Step 1 table says "binary only: ask the user"; the user's request was explicitly to port this ROM, and a 6502 binary can be disassembled, so I took the 6502 row ("translate the code once on the host").
- The 6502 row assumes source or a disassembly fed to amiga68ktools. A ROM has no symbol for its jump tables (a `JSR $C232` followed by a table of addresses), its stack tricks or which bank a call reaches; I had to trace the game in an emulator of my own (`tools/nesref`) to find entry points, then translate statically (`tools/recomp.py`).
- The table promises "50 Hz" for the 6502 route. That holds only if the original CPU is lightly loaded. This game keeps the NES CPU 95-100% busy during fielding (9,000-11,000 6502 instructions a frame). Translated code runs straight-line from chip RAM (no fast RAM, 256-byte cache), about 10-13 colour clocks per 6502 instruction, so one busy NES frame costs more than one Amiga frame. The brief has no row for "6502 game that saturates its CPU".
- The brief wants the host test and the Amiga build to compile the same logic C. Translated to C, a 6502 subroutine call becomes a save/restore of every register and flag through globals; gcc's 68k code for it was 3 times too slow. So the Amiga runs a 68k assembly translation and the host runs the C translation of the same decoded program. The equal checksum is then a proof that the two translations agree, which is stronger than the brief asks, but it is not "the same code".
- The original runs at 60 Hz with no source, so the brief's "smooth" route (rescale constants on the host) is impossible; I used TICKS_PER_SECOND 60.
- Defining TICKS_PER_SECOND in a file that also includes `<proto/dos.h>` collides with dos.h's own TICKS_PER_SECOND 50; the skeleton should name its constant differently.
- A NES game waits for the next frame in the middle of subroutines (a loop polling RAM or $2002). The skeleton's game_tick() must return; the brief says nothing about this. I run the translated main thread as a coroutine on its own stack (src/coro.s), switched at those wait loops. This is neither startup, interrupt nor display code, but the brief does not say whether it is allowed.
- The kit has no split screen. This game's sprite-0 split only switches the tile set, so it could be handled by drawing rows with different tile sets; a game that changes scroll at a split could not be shown with the kit.
- The kit has no sprite multiplexing. I reuse each hardware sprite down the screen by writing further control words into its own sprite list (data in chip RAM, the kit still writes the first ones and the pointers). The brief neither allows nor forbids it.
- The kit fixes the playfield/sprite priority (BPLCON2), so NES sprites that should be behind the background are drawn in front.
- The kit cannot narrow the display window. The NES picture is 256 pixels wide, the view 320; I draw the 32-pixel columns at each side in the backdrop colour.
- Sound: the kit only offers ptplayer (modules and one-shot samples). NES sound is four tone generators driven by register writes, so src/sound.c models the NES APU's timing parts and writes Paula's period, volume and pointer registers directly every frame. The brief neither allows nor forbids audio register access outside ptplayer. Very high NES notes are clamped to Paula's fastest rate (period 124).
- tools/bench.sh copies dist/ to a temporary folder and deletes it, keeping only bench.txt. Debug output (per-tick checksums to find the first tick that differs, as the brief's gate table advises) needs another runner: tools/debug_run.sh.
- vasm cannot relocate a `bsr` to a symbol in another object file ("code reloc out of range" at link time); the brief's example `xref` style only works for data. The translated code includes its helper file so the calls stay in one section.
- `tools/port.sh` and CI assume the game is committed in `original/`. With a copyrighted ROM in a public repository that is not possible, so CI cannot build this port; it builds after `tools/make_assets.sh` on a machine that has the ROM.
- The brief's budget method (sum the percentages of objects) does not cover game logic that is not "15%": here logic alone is 40-85% of a frame per NES frame, and 6 NES frames fall in 5 Amiga frames.
- The brief's "measure after every milestone" gives whole-frame numbers only. To find what to optimise I needed a profiler; a vertical-blank sampler (the obvious one with the kit's hook) is biased toward the wait loop, so a debug-only CIA-B timer sampler was needed (src/prof68k.s). The brief could say this.
- The brief says fast RAM helps "1.2 to 2.2 times"; here 4 MB gave about 2x for translated code, and 8 MB gave exactly the same as 4 MB. The size of the fast RAM does not matter, only that code and data are out of chip RAM.
- "Moving things: sprites first" does not cover a game with 40 small sprites in 4 palettes; the kit has no multiplexing, so cluster-to-attached-pair assignment had to be designed here.
